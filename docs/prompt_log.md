# 생성 AI 활용 및 프롬프트 진행 기록

본 문서는 **LiDAR 장애물 회피 모방학습 시뮬레이터(`lidar-avoidance-ml`)** 프로젝트를 고도화하고 수업 실습 내용과 연계·검증하는 전 과정에서 **생성 AI를 어떻게 설계·지시·검증했는지 순서대로 정리**한 발표용 기록입니다.

---

## 1. 생성 AI 활용 전략 요약

단일 AI에게 전체 코드 작성을 일괄 위임하는 방식 대신, **T3 Code 환경에서 역할별 멀티모델 오케스트레이션(설계 → 구현 → 통합 검증 → 교차 코드 리뷰 → 수정)** 파이프라인을 구축하여 활용했습니다.

- **개발자(사용자)의 역할**: 프로젝트 목표 정의, 교육·시연 관점의 핵심 아이디어 제안(비교 GIF, 반응형 기준선, 난이도별 고정 맵 A/B), 수업 실습 코드와의 연계성 검증, 최종 의사결정
- **생성 AI의 역할 분담**:
  - **코디네이터 · 문서 작성 (`Gemini 4 Neon`)**: 요구사항 정리, 작업 분배·감독, 통합 검증, 한국어 기술 문서(`README.md`, `docs/guide.md`) 직접 집필
  - **설계 (`GPT 6.2 Astra · xhigh` / 초기 `Claude Opus 5.5`)**: 파일 수정 없이 아키텍처·알고리즘·수치 명세 및 검증 기준 수립
  - **코드 구현 (`Claude Opus 5.5 · xhigh` / 초기 `GPT 6.2 Sol`)**: 설계 명세 기반 실제 코드 구현 및 단위·매트릭스 테스트
  - **시각 자료 생성 (`GPT 6.2 Astra` / `GPT 6.2 Sol`)**: 개념 설명용 애니메이션 GIF 및 시각화 스크립트 제작
  - **교차 코드 리뷰 (`GPT 6.2 Astra · xhigh` / 초기 `Gemini 4 Argon`)**: 구현 모델과 **다른 제공사(Cross-Provider)** 모델이 독립적으로 버그·엣지케이스·회귀 감사

## 2. 사전 준비: 멀티모델 오케스트레이션 환경 구축

본격적인 프로젝트 고도화에 앞서, 여러 생성 AI 모델의 강점을 조합하고 품질 관리 절차를 자동화하기 위한 협업 환경을 먼저 설계했습니다.

### 준비 1. 초기 멀티모델 역할 배분 및 실행 안정성 점검

- **주요 프롬프트**
  > *"멀티모델 오케스트레이션 환경을 구성하고자 합니다. 설계는 Claude Opus 5.5(High), 구현 워커는 GPT 6.2 Sol(High), 코드 리뷰는 Gemini 4 Argon(High)으로 역할을 배분해 주세요."*
  > *"하위 모델(Gemini 4 Argon 등)은 터미널에서 직접 호출하는 방식인가요, 아니면 별도 프로토콜을 통해 호출되나요? T3 Code 환경에서 Antigravity 연동을 사용하는 것이 계정 및 보안 측면에서 안전한지 확인해 주세요."*
  > *"이미지 및 GIF 생성 작업은 GPT 6.2 Astra에 배정하고, 한국어 문서 텍스트 작성은 메인 에이전트가 직접 담당하도록 역할을 세분화해 주세요."*
- **AI 처리 및 결정 사항**
  - 사용 가능한 프로바이더와 모델 구성을 점검하고, T3 Code 내장 위임 도구(`delegate_task`)와 공식 프로토콜(`antigravity-acp`) 기반으로 하위 에이전트를 안전하게 호출하는 구조를 확인했습니다.
  - 설계·구현·시각 자료·한국어 문서·코드 리뷰로 역할을 명확히 분리했습니다.

### 준비 2. 감독 프로세스 정립 및 재사용 프리셋(`SKILL.md`) 구축

- **주요 프롬프트**
  > *"오케스트레이션 수행 중 하위 모델이 의도에서 벗어나거나 비효율적인 작업을 시도할 경우, 메인 에이전트가 이를 감독하고 교정하는 구조인가요? 또한 코드 리뷰에서 결함이 발견되면 자동으로 수정 단계로 회귀하나요?"*
  > *"매 작업마다 오케스트레이션 모델 구성을 반복 지시하지 않고, 프리셋 형태로 저장해 재사용할 수 있는 방법을 알려주세요."*
  > *"현재 구독 중인 요금제와 토큰 한도를 고려하여, 각 모델의 강점(대화·설계·코딩·리뷰)을 극대화할 수 있는 최적의 역할 구성을 제안해 주세요."*
  > *"주력 구현과 병렬 보조 구현은 모두 Claude Opus 5.5로 통일하고, 설계(GPT 6.2 Astra)와 구현(Claude Opus 5.5) 모두 추론 강도를 `xhigh`로 설정해 주세요."*
- **AI 처리 및 결정 사항**
  - 메인 에이전트가 **명세 검토 → 파일 수정 범위 분리 → 통합 검증 → 교차 리뷰 피드백 루프(Critical/Major 발견 시 재위임 수정)**를 총괄하도록 운영 규칙을 확정했습니다.
  - 최종 확정된 드림팀 구성을 전역 스킬 파일(`my-orchestration/SKILL.md`)로 저장해, 이후 간단한 트리거 지시만으로 동일한 품질 절차가 자동 실행되도록 준비했습니다.

| 역할 | 모델 | 추론 강도 | 담당 범위 |
|---|---|---|---|
| **코디네이터 · 문서** | `Gemini 4 Neon` | 기본 | 대화, 작업 감독, 통합 검증, 한국어 문서 작성 |
| **설계** | `GPT 6.2 Astra` | `xhigh` | 읽기 전용 아키텍처·알고리즘·검증 명세 |
| **코드 구현** | `Claude Opus 5.5` | `xhigh` | 주력·병렬 코드 구현 및 단위 검증 |
| **시각 자료 / GIF** | `GPT 6.2 Sol` | `high` | 개념 도식·애니메이션 GIF 스크립트 제작 |
| **교차 코드 리뷰** | `GPT 6.2 Astra` | `xhigh` | 구현 모델과 다른 제공사의 독립 코드 감사 |

## 3. 단계별 프로젝트 고도화 및 프롬프트 기록

### 1단계. 기존 프로젝트 현황 파악 및 '사전 이론(5번 탭)' 시각 자료·문서 고도화

기존에 구성된 5탭 구조(수집·학습·테스트·시각화·해석)의 Pygame 시뮬레이터를 이어받아, 처음 접하는 청중도 모방학습 원리를 직관적으로 이해할 수 있도록 이론 설명 탭을 개선했습니다.

#### ① 현황 점검 및 개선 방향 도출
- **주요 프롬프트**
  > *"기존 `lidar-avoidance-ml` 프로젝트의 현재 구조를 파악하고 이어서 작업을 진행해 주세요."*
  > *"현재 상태에서 프로젝트의 교육적·시연 완성도를 높이기 위해 추가하면 좋을 만한 개선점을 제안해 주세요."*
  > *"핵심 기능은 충분하므로, 5번 탭('해석' 이론 가이드)의 구성과 가독성을 중심으로 개선 방향을 진단해 주세요."*
- **AI 분석 결과**
  - 5번 탭의 이미지 정렬 불균형, 외부 링크 시각 단서 부족, 텍스트 위주 설명 구조 등 개선 포인트를 도출했습니다.

#### ② 핵심 개념 비교 GIF 기획 및 멀티모델 구현
- **주요 프롬프트**

### 2단계. 베이스라인(기준선) 고도화: 직진 주행 → 지도 없는 반응형 LiDAR 회피

프로젝트를 독립 작업 공간으로 옮긴 뒤 전체 구조를 재점검하고, 학습 모델의 성능을 공정하게 비교할 수 있도록 기준선 알고리즘을 고도화했습니다.

#### ① 문제 제기 및 요구사항 지시
- **주요 프롬프트**
  > *"현재 프로젝트의 전체 파일 구조와 목적을 파악해 주세요."*
  > *"오케스트레이션 워크플로로 베이스라인 모델을 개선해 주세요. 현재처럼 장애물을 무시하고 직진만 하는 방식 대신, 지도 없이 목적지 방향과 LiDAR 정보만 활용해 간단한 규칙으로 장애물을 회피하는 알고리즘을 기준선으로 적용하고자 합니다."*
- **제약 조건 발생 및 대응**
  - 설계 단계에서 요금제 제약이 발생하자 AI가 임의로 모델을 변경하지 않고 즉시 보고했습니다.
  - **조정 프롬프트**: *"현재 요금제에서는 Claude Fable 5.2를 사용할 수 없으므로, 이번 프로젝트의 설계 역할은 GPT 6.2 Astra(xhigh)로 변경하여 진행해 주세요."*

#### ② 오케스트레이션 실행 (설계 → 구현 → 검증 → 교차 리뷰 → 수정)
- **설계(`GPT 6.2 Astra · xhigh`)**:
  - 학습 모델과 완전히 동일한 28차원 관측(LiDAR 25빔 + 목적지 상대 방향 `sin/cos`·거리)만 사용하는 **무상태 인공 퍼텐셜 필드(APF, Artificial Potential Field)** 기준선을 설계했습니다.
  - 목적지 인력과 근접 장애물 척력을 합산해 단순 장애물은 회피하되, 좁은 통로·U자형 장애물 같은 국소 최솟값(Local Minimum)에서는 한계를 드러내도록 구성했습니다.
- **구현(`Claude Opus 5.5 · xhigh`) 및 문서화(`Gemini 4 Neon`)**:
  - `expert.py`의 `baseline_control()` 교체, UI·CSV 라벨을 `라이다 회피 기준선`으로 통일(기존 `Baseline (미학습)` CSV 하위 호환 유지), `results/benchmark_20maps.csv` 재측정, `docs/guide.md` 및 `README.md` 동기화.
  - **20맵 평가 성능 변화**: 기존 직진 기준선 **20%(4도착 · 16충돌)** → 신규 라이다 회피 기준선 **85%(17도착 · 0충돌 · 3시간초과)** (단순 규칙으로 Linear 35%·KNN 80%를 앞서지만, A\* 교사로부터 학습한 RandomForest·MLP·1D CNN의 100%에는 못 미치는 설득력 있는 기준선 확립).
- **교차 코드 리뷰(`GPT 6.2 Astra · xhigh`)가 발견한 결함 및 수정(`Claude Opus 5.5`)**:
  - **`[Major]` 평가 시드 중복(데이터 누수) 차단**: 실시간 수집용 랜덤 맵 시드 카운터가 `1000`에서 시작해 20맵 평가용 시드(`1000–1019`)와 19개 겹치던 기존 잠재 버그를 발견 → 실시간 랜덤 맵 시드를 `2000`번대로 분리하고 `1000–1019`를 명시적으로 건너뛰도록 수정(`app.py`).
  - **`[Minor]` 방어 가드 보강**: `NaN`/`inf` 관측값, `goal_dist <= 0`, `num_beams <= 0` 엣지 케이스 처리 추가 및 요약 차트 x축 라벨 겹침 해소(`visualizer.py`).

### 3단계. 테스트용 고정 맵 A(Easy) · B(Hard) 재설계

시연 및 발표에서 **"단순한 환경에서는 어떤 모델이든 통과하지만, 복잡하고 변수가 다양한 환경에서는 잘 학습된 모델이 반드시 필요하다"**는 핵심 메시지를 직관적으로 보여주기 위해 고정 맵을 재설계했습니다.

#### ① 문제 제기 및 방향 합의
- **주요 프롬프트**
  > *"테스트 탭의 고정 맵 A, B를 난이도 대비가 뚜렷하게 재설계하고 싶습니다. 맵 A는 대부분의 모델이 통과할 수 있는 기본 회피 코스로, 맵 B는 충분히 학습된 모델만 통과할 수 있는 복합 난코스로 구성하여 복잡한 환경에서의 모델 학습 중요성을 보여주면 어떨까요?"*
  > *"제안한 설계 방향대로 오케스트레이션으로 진행해 주세요."*
- **AI 사전 실측**: 기존 고정 맵 A/B에서 모든 모델을 실행한 결과, 맵 A에서는 Linear가 충돌하고 맵 B에서는 기준선과 KNN까지 모두 통과해 난이도 대비가 흐려져 있음을 정량적으로 확인한 뒤 설계에 착수했습니다.

#### ② 오케스트레이션 실행 및 전수 검증
- **설계(`GPT 6.2 Astra · xhigh`)**:
  - **고정 맵 A · 기본 회피 (Easy)**: 목적지 직선 위에 원형 장애물을 배치해 단순 직진 주행은 1.9초 만에 충돌하지만, 기본 회피 능력만 있으면 전원 통과 가능한 구조
  - **고정 맵 B · 복합 난코스 (Hard)**: 대각선 경로에 엇갈린 장애물 군집과 다중 통로를 배치해 모델 역량별 3단 격차가 뚜렷하게 갈리는 구조
- **구현 및 616회 매트릭스 검증(`Claude Opus 5.5 · xhigh`)**:
  - 회귀·분류 × 30Hz·60Hz × 노이즈 OFF/ON(10개 시드) × 7개 주행기(기준선 + 5종 모델 + A\* 교사) = **총 616개 에피소드 100% 일치 검증**
  - **맵 A 결과**: 7종 전원 도착 (직진 주행 시 충돌)
  - **맵 B 결과**:
    - `라이다 회피 기준선`: 충돌 없이 **18초 시간 초과** (국소 최솟값 한계)
    - `Linear`, `KNN`: **충돌** (선형·단순 이웃 기반 모델의 한계)
    - `RandomForest`, `MLP (DL)`, `1D CNN (DL)`, `A* 교사`: **전원 도착**
  - 버튼 텍스트 폭(116px 제한)에 맞춰 UI 라벨을 `A · 기본 회피`, `B · 복합 난코스`로 확정.

  > *"현재 프로젝트에 이미 실습 코드의 모델과 방법이 포함되어 있는지, 그리고 동일한 모델이 코드 수준에서 어떻게 다르게 구현되어 있는지 비교해 주세요."*
  > *"실습 코드와 현재 프로젝트의 전체 모델 목록을 대조하여 동일한 모델과 확장·추가된 모델을 정리해 주세요."*
- **AI 분석 및 시뮬레이터 실측 결과**
  - 노트북 전체 217개 셀의 핵심 모델 3종(`LinearRegression`, `LogisticRegression`, `KNeighborsClassifier`)과 전처리 도구(`StandardScaler`, `PCA`, `NumPy`)를 식별했습니다.
  - **노트북 코드 패턴만**을 프로젝트 데이터셋(`data/dataset.npz`)에 적용해 20맵 및 맵 A/B에서 실제 주행을 측정했습니다.

    - `predict_proba` + `@`(행렬곱) 연속 조향 응용: 20맵 **95% (충돌 0회)**
  - **실습 코드 vs 현재 프로젝트 모델 1:1 대조**:
    - **동일 / 동일 계열 모델**: `LogisticRegression` (Linear 분류), `KNeighborsClassifier` (KNN 분류), `LinearRegression` → `Ridge` (Linear 회귀, L2 규제 추가) + `StandardScaler` · `PCA`
    - **실전 고도화 차이**: 실시간 60fps 주행·체크포인트 저장·불균형 데이터 대응을 위해 `Pipeline` 래핑, `class_weight="balanced"`, `KNeighborsClassifier(k=7, weights="distance", algorithm="kd_tree")`, 좌우 반전 데이터 증강 적용
    - **프로젝트 확장·추가 모델**: `KNeighborsRegressor` (KNN 회귀), `RandomForest` (분류·회귀), `PyTorch MLP / 1D CNN` (분류·회귀), 규칙 기반 `라이다 회피 기준선(APF)`

## 4. 생성 AI 활용을 통해 얻은 핵심 인사이트 (발표 요약용)

1. **구체적인 문제 의식이 결과물의 완성도를 결정한다**: 막연한 개선 요청이 아니라 *"전역 지도를 아는 A\*와 미지 환경의 학습 모델을 대비하는 GIF"*, *"맵 A는 누구나 통과하고 맵 B는 잘 학습된 모델만 통과하는 난이도 대비"*처럼 **명확한 시연 시나리오와 기준을 제시**했을 때 가장 효과적인 결과물을 얻을 수 있었습니다.
2. **교차 모델 리뷰로 숨은 결함을 조기에 차단했다**: 구현 모델(`Claude`)과 다른 제공사 모델(`GPT`)에게 독립 코드 리뷰를 수행하게 함으로써, **평가용 시드와 수집용 시드의 중복(데이터 누수 위험)** 및 **프리셋 맵 참조 공유 버그**처럼 겉으로 드러나지 않는 결함까지 발견하고 수정할 수 있었습니다.
3. **수업 기초 이론에서 실전 딥러닝까지 일관되게 확장했다**: 수업 실습 노트북의 `LinearRegression`, `LogisticRegression`, `StandardScaler + KNN`만으로도 시뮬레이터 주행 모델이 실제로 작동함을 정량 검증하고, 나아가 복잡한 환경(맵 B)에서 왜 `RandomForest`와 딥러닝(`MLP`, `1D CNN`)으로 확장해야 하는지 설득력 있는 비교 스토리를 완성했습니다.
